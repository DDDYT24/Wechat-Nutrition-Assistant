# 普通微信营养助手 V1.1 计划

## 1. 目标

使用专用普通微信测试小号作为聊天入口。好友在原生私聊窗口发送以“营养助手”开头的文字后，消息通过 `wangrongding/wechat-bot` 的 Wechaty 网页协议进入本机营养服务。

DeepSeek 只负责理解和表达；热量、蛋白质、脂肪、碳水、餐次和每日累计由受控食物目录与确定性程序计算。

## 2. V1.1 架构

```text
微信好友私聊
  -> 专用测试小号扫码登录
  -> wechat-bot / Wechaty / wechat4u
  -> Nutrition adapter
  -> 本机鉴权 POST /internal/chat
  -> NutritionAgent
       -> 用户授权与资料二次确认
       -> DeepSeek 结构化理解
       -> 食物目录与确定性营养计算
       -> 餐次、每日累计和趋势数据库
  -> 微信纯文本回复
```

公众号通道继续保留为回退，不影响普通微信实验。

## 3. V1.1 范围

- 只处理私聊文字。
- 所有用户必须使用前缀“营养助手”。
- 群聊、主动群发、朋友圈、图片、语音和自动接受好友默认关闭。
- 首次使用需同意健康数据处理说明，并乱序提交资料后再次确认。
- 使用 Mifflin–St Jeor 公式与活动系数计算初始能量目标。
- 按上海时间自动划分早餐、中午、下午和晚上。
- 回复本餐及当日累计热量和三大营养素。
- 未知食物或重量不足时追问，绝不让大模型编造营养数字。

## 4. 安全与限制

- `wechat-bot` 使用非官方微信网页协议；能否登录取决于小号是否拥有网页版登录权限。
- 仓库作者明确提示该协议存在微信警告或封号风险，因此只使用专用测试小号。
- 登录二维码仅在本机生成，不发送到第三方二维码网站。
- DeepSeek API Key 只保存在根项目 `.env`，微信桥接进程无法读取或输出该 Key。
- 桥接只允许访问 `127.0.0.1`，使用由 `USER_HMAC_SECRET` 派生的临时 HMAC Token。
- 微信正文不写入 wechat-bot 日志或 JSONL；业务数据库只保存 HMAC 化用户标识。
- 同一微信消息使用消息 ID 幂等，避免重复记餐。

## 6. 验收标准

- 非前缀私聊、群聊和机器人自己的消息不触发回复。
- “营养助手 米饭100g”进入授权或记录流程。
- 同一条微信消息不会重复记餐。
- 回复包含本餐及当天累计热量、蛋白质、脂肪和碳水。
- 未提供重量或食物未收录时不输出伪精确结果。
- DeepSeek 不可用时返回确定性降级说明，不返回 500，也不编造数据。

## 7. 回退

若小号没有网页版登录权限，或微信出现风险提示，立即停止 Wechaty 进程并继续使用现有公众号。届时不再回退到旧版 WCF 注入方案。
