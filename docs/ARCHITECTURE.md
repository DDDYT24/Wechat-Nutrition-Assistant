# V1.2 架构与数据边界

本文件是项目设计的权威说明。产品使用方式见 [README](../README.md)，尚未解决的问题见
[KNOWN_ISSUES](KNOWN_ISSUES.md)。

## 处理链路

```text
微信 / 本地桥接 / MCP
          │
          ▼
    NutritionAgent
          │
          ├── 可选 LLM：提取意图、估算目录外食物、回答饮食问题
          │
          ├── 规则解析器：食物、份量、训练字段
          │
          ├── 受控目录、模型估算与计算服务
          │
          ▼
       Repository
          │
          ▼
   已保存记录生成回复、日报和周报
```

## 职责边界

### 语言模型

DeepSeek 负责识别饮食、训练和查询意图。目录未命中时，它可以估算常见份量和每 100 克营养值；估算
必须通过范围校验并以 `estimated` 来源保存。它也可以基于数据库提供的当日累计、剩余额度、目标、
过敏和偏好回答“还能吃多少”及“下一餐吃什么”。训练消耗不交给模型计算。

模型不可用、超时、返回目录外名称或伪造非原文片段时，Agent 忽略该结果并回退到规则解析。

### 食物解析

目录为每个别名保存候选项，但规则解析每次只取一个确定候选。匹配按原文中的最长非重叠区间进行，
避免“鸡蛋”同时命中多个鸡蛋条目或内部的“鸡”。优先级为：

1. 精确标准名；
2. 目录明确标记的代表值；
3. 稳定排序后的单个候选。

没有合适目录项的食物优先调用模型估算，不再默认要求用户补录目录。回复必须明确标注模型估算，方便
用户理解配方和份量偏差。

### 数值计算

- 食物热量和宏量营养优先来自受控目录或包装标签；目录外食物可使用经过范围校验的模型估算。
- 份量换算来自代码内的单位规则，不采用模型估算。
- 训练消耗依据受控 MET、已保存体重、时长和强度确定性计算。
- 每日余额、营养缺口和周报只汇总数据库中的已保存记录。
- 训练消耗与饮食摄入分开呈现，不自动增加可摄入预算。

### 多意图编排

Agent 先识别全部意图，再分别处理餐食和训练，最后合并回复。单个意图缺少信息时，不得阻止其他已经
确定的意图保存。例如“一个鸡蛋，一碗米饭，半碗粥；训练90分钟”会保存鸡蛋、米饭和训练，同时询问
粥的种类。

### 持久化与隐私

`Repository` 是业务记录的唯一持久化入口。用户标识先通过 HMAC 转为伪匿名键；数据库不保存原始
OpenID。餐食与训练写入均接受 `source_message_id`，微信重试同一消息时返回已有记录而不重复累计。

主要持久化数据包括用户资料草稿、确认资料、餐食及明细、训练、体重、自定义食物和异步结果。删除
用户数据依赖外键级联，并且只能在用户明确确认后执行。

## 接口边界

`NutritionService` 同时服务微信 Agent、HTTP 入口、MCP 和测试，避免各通道复制计算逻辑。MCP 只是
受控服务接口；`record_exercise` 不接受消耗数字，`save_meal` 不保存未解析的目录项。

Agent 的运行时操作约束位于 [track-healthy-diet Skill](../skills/track-healthy-diet/SKILL.md)。Skill
可以重复最关键的安全不变量，但不承担项目介绍、版本历史或部署说明。

## 验证策略

- 单元测试覆盖目录、份量、计算、服务和结构化模型边界。
- Agent 回归测试覆盖混合意图、重复消息和降级路径。
- 进程级测试启动真实 Uvicorn，验证健康检查、公众号签名和 XML 往返。
- Node 测试验证普通微信适配器的消息元数据、本地地址限制和安全降级。
- 真实账号权限、微信平台行为和公网质量必须人工验收。
